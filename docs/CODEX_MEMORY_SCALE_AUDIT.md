# WhatsApp assistant: memory, context and scale audit

Audit date: 2026-09-21. Source cutoff: **00:32:28 UTC / 02:32:28 Europe/Madrid**. Scope: the working tree on `main`, HEAD `b2eb3523754030e86f1480b8252f23ae2c08253e`, including uncommitted changes captured at that cutoff. All nine requested files were read, together with directly connected ingestion, policy, configuration, retrieval and reminder code. References are repository-relative `file:line` locations in that snapshot; source fingerprints below identify the moving files.

**Assessment:** the bot has durable workflow memory and a newly added factual-memory prompt, but incomplete conversational memory. A process restart or a few days of silence does not itself reset a case. The largest concurrent-client risk in the captured code is the shared mutable memory string: one client can overwrite the facts later used for another client’s reply. Other serious risks are support replies invalidating business actions and shared dispatch work being interrupted by contention on one case.

This is a static source audit, not a production capacity certification. No services, provider calls, client messages, database mutations or mock tests were run. The local RAG metadata and vector-file size were inspected read-only. Defaults are identified as defaults; deployed settings, migrations, replica count, DB pool limits, query plans, provider quotas and live latency remain unverified. Only this report was written by this audit. Concurrent edits added case-memory plumbing, a draft memory migration, a backlog check change and a fallback-notice recursion guard; their code was re-read at the stated cutoff. These changes are not claimed deployed or verified end to end. Later edits are outside this audit snapshot.

**1. What the bot remembers, and what it forgets**

The durable unit is `BotApodExpediente`, selected by the sender's telephone number, not an ephemeral model session. Both `dni` and `telefono` are unique. This supports many distinct clients, but currently permits only one workflow record per DNI/phone, rather than multiple independent matters for the same client. Linking a second project with the same identity/phone is rejected. Evidence: `prisma/schema.prisma:32-45`; `src/api/server.ts:203-204`; `src/core/workflow-service.ts:26-37`.

| Memory | Persisted between process restarts/days | What the conversation model receives |
|---|---|---|
| Identity and selected matter | DNI, name, telephone, Kmaleon project, company, business case number, source, identity verification; address/geography and judicial district. | No full structured identity/matter/address object. The new factual memory includes the DNI/NIE **type**, not the identifier. Recognizable personal information in chat text is redacted. |
| Workflow position | `currentState`, `version`, `stepReached`, `stepEnteredAt`, `previousState`. New `pendingQuestion` and its timestamp. | `currentState`, a derived next-step sentence, and `stepReached`/last question via the new memory string. No business version or previous-state field. |
| Certificate/help facts | `hasDigitalCert`, `certDevice`, `digitalHelpAttempts`, `certificateHelpAttempts`. | Certificate yes/no/unknown in both calls; both help counts explicitly in the reply call. New factual memory also carries device and either copy-help or digital-help count. |
| Consent | Granted flag, version and timestamp. | New factual memory says consent is granted when its flag is true. It does not supply the consent version, time or bound evidence. |
| Documents and partner progress | Current document pointer, audit status/page count, approval/client-review flags, provisional status, partner order/preapproval/expiry/evidence; document rows hold hashes, storage paths and filing/approval proofs. | New factual memory can say the document is approved. No document contents, audit report, filing receipt, partner order or payment evidence is supplied. |
| Contact and human review | Last inbound/outbound, prior-conversation flag, reminder cycle/anchor/count/day/next date, pause/opt-out flags; human tasks and audit records. | Factual memory includes an already-started/silence hint, but no reminder schedule, pause reason, task resolution or operator notes. The silence hint has a timing defect discussed below. |
| Transcript and effects | Minimized user text; accepted outbound text; inbox event payloads; action payloads, status, retry counts and receipts; transition audit history. | At most 12 selected transcript rows, further bounded to 12,000 characters. Inbox/action/audit histories are not generally retrieved for the model. |

Persistence evidence: `prisma/schema.prisma:32-100`, `prisma/schema.prisma:102-202`. The model boundary is explicit at `src/core/conversation-agent.ts:28-50`, `src/core/conversation-agent.ts:109-119`, `src/core/conversation-agent.ts:157-168`; prompt construction is at `src/adapters/ai/openai-compatible-conversation.ts:68-87` and `src/adapters/ai/openai-compatible-conversation.ts:235-270`. FSM facts are copied into an allowlisted persistence patch at `src/core/workflow-service.ts:57-79`.

**The 12-message limit is a retrieval limit, not transcript deletion.** The worker fetches the newest 12 eligible rows, reverses them into chronological order, and excludes the rows being processed. User history must precede the source message's timestamp; assistant rows are eligible regardless of that cutoff. Those are 12 individual messages, not 12 complete exchanges. A burst of user messages or reminders can use much of the window (`src/core/workflow-service.ts:225-234`).

There is a second limit: the policy retains at most 2,000 characters per message and 12,000 total, starting with the newest messages. Six full-length messages can therefore exhaust the budget. Redaction is reapplied and recognized injection content becomes a placeholder (`src/core/conversation-policy.ts:35-89`). User transcript storage is already capped at 2,000 characters, although the phase-3 inbox retains the redacted current text and accepts individual text messages up to 4,000 characters. A grouped turn is capped at 4,000 characters (`src/core/debounce-buffer.ts:17-22`; `src/adapters/whatsapp/webhook-router.ts:17-20`; `src/core/workflow-service.ts:192-202`).

Older transcript rows remain available in the database; they are **not summarized or semantically retrieved as client memory**. The new schema now declares `conversationSummary`, `conversationSummaryAt` and `conversationSummaryTurns`, with an added migration, but no producer or reader of those fields appears in the captured runtime. The new `caseMemory(c)` builds a string from existing structured facts; it does not summarize older dialogue. Thus there is a summary-shaped storage slot, but no functioning rolling per-case summary (`prisma/schema.prisma:76-82`; `prisma/migrations/20260921000000_conversation_memory/migration.sql:3-8`; `src/core/case-memory.ts:11-29`; `src/core/workflow-service.ts:225-234`). The decision’s `auditTrailSummary` is a single-transition explanation stored with the audit decision, not a dialogue summary (`src/core/decision-engine.ts:225-236`; `src/core/workflow-service.ts:78`). The operator messages endpoint returns only the oldest 300 rows without pagination (`src/api/automation.routes.ts:38`).

Consequently, older client constraints—who will help, the precise error/screen, their chosen certificate-acquisition subroute, appointment date, a request to wait until a particular day, or the meaning of “the first option”—drop out unless represented by an existing structured field. Deferral text only yields an acknowledgement; it does not persist a client-requested resumption date (`src/core/conversation-guidance.ts:16-23`). Declared DNI/NIE guidance is reconstructed from the current text or the last matching user text in the loaded history and added to that event payload; it is not a case fact (`src/core/conversation-agent.ts:192-195`; `src/core/workflow-service.ts:61-62`). A verified stored DNI still exists and is used by deterministic identity-dependent routes (`src/domain/fsm/state-machine.ts:324-337`).

There are two useful qualifications:

- Opening detection deliberately searches across all accepted `ASK_HAS_CERT` receipts and matching assistant messages, outside the 12-message window. This is a durable “already introduced” check, not a summary. `priorConversation` itself does not control that check (`src/core/workflow-service.ts:227-234`). Importing history sets `priorConversation` but does not reconstruct FSM facts (`src/api/automation.routes.ts:43-48`).
- Stored assistant messages mean **API-accepted**, not necessarily delivered: they are inserted with source `OUTBOX_ACCEPTED` while the action enters `AWAITING_DELIVERY`. The history passed onward drops source, timestamp and delivery provenance. Approved Meta templates store a marker such as `Plantilla aprobada: ASK_HAS_CERT`, not their rendered question. Official links retained by the outbound-history helper are redacted again by the generic model-history boundary (`src/queue/action-executor.ts:109-118`, `src/queue/action-executor.ts:154-157`; `src/core/workflow-service.ts:234`; `src/core/outbound-history.ts:14-20`; `src/core/conversation-policy.ts:69-83`). The model may therefore be missing the exact question the client saw—or may assume an accepted but failed message was seen.

**Exact provider context:** optional training-package system prompt; optional master workflow prompt; runtime classification or reply instructions; up to five historical training examples; bounded transcript entries wrapped as untrusted JSON `user` messages; the new case-memory JSON message; then the redacted current client text. The memory message is outside the 12-message/12,000-character history budget. There is no provider thread ID, continuation token or tool execution interface. Every completion reconstructs context (`src/adapters/ai/openai-compatible-conversation.ts:77-89`, `src/adapters/ai/openai-compatible-conversation.ts:242-275`).

The new pending-question persistence extracts the last question ending in `?` only when it is **8–200 characters** long and saves it on API acceptance. A message without a qualifying question does not clear the previous one; approved-template markers contain no rendered question. It is therefore not a complete pending-dialogue contract (`src/core/case-memory.ts:32-36`; `src/queue/action-executor.ts:113-118`, `src/queue/action-executor.ts:154-157`). The summary migration’s presence does not establish that the live DB has these columns; deployment/migration status was not checked.

The factual-memory helper also has two concrete mistakes: `certDevice='NONE'` is truthy and rendered as “on the computer” because every non-`MOBILE` value takes that branch; and elapsed silence is computed from `lastInboundAt` after ingestion has normally updated it to the returning message, so a client returning after days ordinarily gets a zero-day gap (`src/core/case-memory.ts:18`, `src/core/case-memory.ts:25-28`; `src/core/debounce-buffer.ts:20-21`). These facts can contradict the otherwise-correct saved state.

RAG retrieves **training examples**, not this client's old messages. Its query uses only the first 700 characters of the current client text, without saved state or transcript. A classify-then-reply turn can repeat the same retrieval (`src/core/package-agent/rag-index.ts:15-16`, `src/core/package-agent/rag-index.ts:124-136`; `src/adapters/ai/openai-compatible-conversation.ts:247-251`). It does not learn new client facts as conversations happen.

**2. Why a client returning after days resumes, and where that fails**

The normal phase-3 path is: sender phone → existing case → durable inbox → quiet period → per-case lock → freshly loaded case → local policy/model proposal → deterministic FSM → transactional case update, audit, outbox action and consumed inbox status. No elapsed-time reset appears in this path (`src/api/server.ts:203-211`; `src/core/debounce-buffer.ts:11-28`; `src/core/workflow-service.ts:169-189`, `src/core/workflow-service.ts:254-266`).

Greetings use `pendingConversationText`; an opening is selected only when not already introduced, in initial/certificate triage, without a known certificate. A brief yes/no is interpreted against the stored state—for example, in `MOBILE_TRIAGE_PC_CHECK`, “sí” means PC availability. Certificate/device transitions persist their facts. Repeated `CASE_OPENED` outside initial triage holds rather than restarting (`src/core/conversation-agent.ts:201-208`; `src/core/messages.ts:28-40`; `src/core/conversation-policy.ts:203-209`; `src/domain/fsm/state-machine.ts:289-313`, `src/domain/fsm/state-machine.ts:1268-1269`).

| Return scenario | Actual behavior / failure boundary |
|---|---|
| Same known number, several days later, automation active | Reloads saved state. Ingestion updates `lastInboundAt` monotonically and resets the reminder cycle; it does not reset workflow facts (`src/core/debounce-buffer.ts:20-23`). |
| “Yes” to an old question | Still interpreted locally against today’s state. Although webhook normalization captures `contextId`, the ordinary phase-3 payload omits it. The newly stored `pendingQuestion` reaches the model through memory but is not bound to an action ID/answer-kind and is not consulted by the deterministic yes/no classifier. A reply to an older quoted question can be misread (`src/adapters/whatsapp/webhook-router.ts:40-41`; `src/api/server.ts:208-211`; `src/core/conversation-policy.ts:203-209`; `src/core/case-memory.ts:24`). |
| Consent/draft approval after hours or days | The approval must match the original action/template/current case version. The worker additionally rejects a request action created more than **3,600,000 ms (one hour)** ago. Age is measured from action creation, not delivery, so queue delay consumes the window. The row becomes `HUMAN_REQUIRED`; this branch does not automatically issue a fresh approval request (`src/api/server.ts:238-243`; `src/core/workflow-service.ts:248-251`). |
| Consent after an intervening support exchange | A same-state support reply still increments `version`, invalidating the earlier request's version even within one hour (`src/core/workflow-service.ts:74-79`; `src/api/server.ts:242`). |
| After a human handoff | State is saved in `previousState`, automation pauses, and ordinary new text becomes `HUMAN_REQUIRED`; one acknowledgement per case version is queued. It does not automatically replay those texts after recovery (`src/core/workflow-service.ts:66`, `src/core/workflow-service.ts:212-222`, `src/core/workflow-service.ts:154-166`). |
| Recovery from a handoff | Requires explicit operator recovery. Missing/initial `previousState` is rejected; the FSM also forbids recovery directly into completed/filing/notice/provisional states. Recovery produces no immediate client message or automatic replay of a prior external action. This preserves evidence gates but requires an operator continuation procedure (`src/core/workflow-service.ts:154-165`; `src/domain/fsm/state-machine.ts:114-120`, `src/domain/fsm/state-machine.ts:1168-1193`). |
| “I will not share it” while escalated | A special regex unpauses the case before classification. Its consent-denied event is then held by the escalated-state handler, which requires operator resume. The intended shortcut does not restore the saved workflow; it can leave `ESCALATED_HUMAN` with `automationPaused=false` (`src/core/workflow-service.ts:208-212`; `src/core/conversation-agent.ts:213-215`; `src/domain/fsm/state-machine.ts:1188-1193`). |
| Thirty days of silence | With reminders enabled and a due eligible case, management review pauses automation without resetting the FSM. A later message does not unpause it. Resolving the management task and resuming automation are separate operations (`src/core/automation.ts:9-24`; `src/api/automation.routes.ts:14-35`). |
| New/unmatched number | No automatic new case: inbox becomes `UNMATCHED`. Manual linking only updates the inbox; it does not backfill the omitted transcript/last-inbound update performed for a matched ingestion (`src/core/debounce-buffer.ts:17-23`; `src/api/server.ts:183-187`). |
| A missing or uncertain previous send | Text consumption can stop behind that action, even days later. `PENDING`, `RUNNING` and `UNCERTAIN` WhatsApp actions block the inbox (`src/core/workflow-service.ts:183-185`). |

Automatic follow-ups use saved step/cycle/anchor at days **3, 7 and 15**, then management review at day **30**; after downtime only the latest due reminder is proposed. The executor rechecks for new inbound before sending. These are separate from the pure FSM's reminder handlers, so the actual scheduled behavior follows `FOLLOW_UP_STATES` and `canFollowUp` (`src/core/follow-up.ts:4-21`; `src/core/automation.ts:26-30`; `src/queue/action-executor.ts:63-66`, `src/queue/action-executor.ts:94`).

The sender enforces its own **24-hour** rule: outside the window, Meta delivery requires an approved template; the emulator bypasses that branch. A genuinely new inbound normally refreshes the window, but an old provider timestamp, unlinked-message recovery, or a reply delayed more than a day can leave it closed (`src/core/debounce-buffer.ts:20-21`; `src/queue/action-executor.ts:152-157`). This describes the implementation, not independent verification of Meta policy.

**3. Concurrent-client limits, bottlenecks and races**

| Component | Limit implied by this checkout | Operational consequence |
|---|---|---|
| Text debounce | Default **60,000 ms**; configurable **1,000–120,000 ms**. Every new text postpones all pending texts for that case. Buttons/media **4,000 ms**; opt-out **0 ms** (`src/core/conversation-batching.ts:4`; `src/config/env.ts:28`; `src/core/debounce-buffer.ts:13-19`). | At least one minute after the last text by default, plus processing/dispatch. No maximum burst age; continued messages can postpone a case indefinitely. The worker also waits if any of the fetched 50 rows is not due. |
| Inbox batching | **50** pending rows fetched per case; related texts merge only with identical `notBefore`, topic compatibility and total **4,000 characters** (`src/core/workflow-service.ts:173-202`; `src/core/conversation-batching.ts:36-45`). | Separate subjects remain separate turns. The cutoff code distinguishes older backlog using `snapshotAt`, replacing the original non-draining “outside this page” test; residual timing concerns are below. |
| Redis workflow locks | `lock:apod:<caseId>` and separate `lock:apod-inbox:<caseId>`, each **180,000 ms** (`src/core/workflow-service.ts:24`, `src/core/workflow-service.ts:170`). | Different cases can run concurrently; one case serializes classification, sends, document work, reminders and operator events. Text processing holds both locks during provider calls. |

It renews leases; 180 seconds is not a hard task deadline (`node_modules/redlock/dist/esm/index.js:271-290`, `node_modules/redlock/dist/esm/index.js:419-450`). A long-running case readily exceeds competitors' acquisition budget. |
| Workers per process | Inbound **4**, PDF audit **2**, Kmaleon **4**, notifications **4**; job lock duration **180,000 ms** (`src/queue/workers.ts:11-24`). | **14 job slots per process**, not 14 CPU threads, DB connections or conversations. | Dispatch | Every **5 seconds**, no overlapping tick within a process; up to **100** due follow-up cases, **200** delivery callbacks, **100** inbound recovery cases, **50** audit documents, **100** pending actions (`src/core/automation.ts:11`; `src/queue/workers.ts:34-48`). | These are batch sizes, not throughput guarantees. Loops are sequential; slow/failed early work delays everything later. The ticking flag is process-local, not a distributed dispatcher lock. |
| Queue recovery/retry | **3** BullMQ attempts, exponential backoff starting **2 seconds**; **1,000** completed/failed jobs retained per queue; dead letters retained without automatic removal (`src/queue/queues.ts:3-10`). | Durable DB rows recover scheduling gaps, but worker retry settings do not ensure retries of executor failures that are caught and persisted. |
| Provider | Default **60 seconds per attempt**, up to **2 attempts** when the result is null; embedding timeout at most **8 seconds**. An unsupported classification can be followed by a reply call (`src/config/env.ts:29`; `src/adapters/ai/openai-compatible-conversation.ts:142`, `src/adapters/ai/openai-compatible-conversation.ts:242-256`; `src/core/conversation-agent.ts:277-281`). | One model operation can approach **128 seconds**; classify plus reply can approach **256 seconds**, excluding DB/CPU/queue delay. No aggregate turn deadline, provider-wide limiter, retry backoff or circuit breaker here. Syntactically valid but policy-invalid JSON is not necessarily retried. |
| Other long work | Generic HTTP default **30 seconds**; Kmaleon ordinary/auth defaults **120 seconds per request**; PDF audit default **30 seconds**, concurrency 2 (`src/adapters/common/http.ts:33-36`; `src/config/env.ts:30`; `src/core/pdf-auditor.ts:45-46`; `src/queue/workers.ts:23`). | External effects and PDF work also occupy case locks. Multi-request effects can take longer than a single request timeout. |

At four inbound slots, if every turn consumes 256 seconds, the idealized service rate is only **4 × 60 / 256 ≈ 0.94 turns/minute per process**, before contention or dispatch delays. A single 128-second operation per turn implies **1.88 turns/minute**. These are arithmetic illustrations of timeout exposure, not measured throughput. Local deterministic turns can be much faster. Streaming is assembled into one JSON result before the workflow commits; it does not stream partial WhatsApp answers (`src/adapters/ai/openai-compatible-conversation.ts:91-126`, `src/adapters/ai/openai-compatible-conversation.ts:280-281`).

**Critical shared-memory race:** the HTTP server installs one `StrictConversationAgent` on the shared workflow service. Each case assigns `conversationAgent.memory = caseMemory(c)`. Different cases have different Redis locks and four inbound slots. If case A is awaiting model classification, case B can replace that field; when A falls through to `respond()`, it reads B’s memory for its reply request. A’s state/text/history can then be sent alongside B’s saved facts/question. The request inputs are strings once constructed, but the second construction reads the mutable shared field again. This creates a concrete cross-case context path; it does not require the RAG index to mix client data (`src/api/server.ts:79-81`; `src/core/workflow-service.ts:233-234`; `src/core/conversation-agent.ts:58-60`, `src/core/conversation-agent.ts:118`, `src/core/conversation-agent.ts:167`, `src/core/conversation-agent.ts:277-281`; `src/queue/workers.ts:11-22`). No live cross-client test was run.

**Backlog change at the cutoff:** the earlier code counted any pending ID outside the first 50 rows as a new arrival, so 51 already-due texts could prevent every commit. The captured replacement uses `snapshotAt = new Date()` after the fetch and checks non-consumed rows whose `notBefore` is still future or `createdAt > snapshotAt`. The original 51-row starvation finding therefore no longer applies unchanged; no real backlog replay was run (`src/core/workflow-service.ts:173-177`, `src/core/workflow-service.ts:254-265`). Residual risk: an arrival between the SELECT and `snapshotAt`, or a transaction begun before that application-clock timestamp but committed afterward, can be absent from the fetched page yet fail the strict timestamp test once its quiet period expires. Cross-host/DB clock differences also weaken this boundary. A monotonic arrival generation captured under the existing row lock would avoid these timestamp gaps. Ongoing text can still postpone all pending text indefinitely; there is no maximum burst age (`src/core/debounce-buffer.ts:13-19`).

**One case can impede all cases through the dispatcher.** `dispatch()` calls `scheduleFollowUps()` first, then processes callbacks one at a time. Both can attempt a workflow lock held by a model turn. If lock acquisition throws, the single outer catch skips inbound recovery, audit scheduling and pending-action dispatch for that tick. Recovery queries also have no fairness cursor; a persistent set of stuck cases can repeatedly occupy the 100-case batch. Existing queued jobs may still execute, but new durable work can wait (`src/queue/workers.ts:35-47`; `src/core/automation.ts:12-14`; `src/queue/action-executor.ts:246-250`).

The intended race defenses are substantial: Redis serialization, compare-and-swap on case version, action status/retry-count claims, transactional outbox/inbox commits, unique provider message IDs, and a shared PostgreSQL row lock between ingestion and the final draft check (`src/core/workflow-service.ts:74-79`, `src/core/workflow-service.ts:254-265`; `src/core/debounce-buffer.ts:9-26`; `src/queue/action-executor.ts:100-110`). The provider call is outside the SQL transaction: it holds Redis locks but does **not** pin a database transaction/connection for the whole model wait. Lock loss is checked after generation, but the model fetch receives only its own timeout signal, so it continues spending time/quota until it returns (`src/core/workflow-service.ts:234-235`; `src/adapters/ai/openai-compatible-conversation.ts:255-276`).

Remaining boundaries include arrival order versus provider time: inbox ordering uses local `createdAt`/ID, while user-history cutoff uses provider message time. Earlier messages sharing the same provider second can be excluded by strict `<`; delayed webhooks can be processed after newer messages. Ordinary text loses quoted-message context. Also, the pending-WhatsApp-action check occurs before acquiring the case lock, so it is not a fully atomic guard against an operator creating another outbound action in between (`src/core/workflow-service.ts:173`, `src/core/workflow-service.ts:185-189`, `src/core/workflow-service.ts:226`; `src/core/debounce-buffer.ts:20-22`; `src/api/server.ts:211`).

**Database capacity is unspecified.** There is one module-level `PrismaClient` per application process, with only logging configured; the main process shares it between HTTP and workers. The checked-in Compose URL specifies only `schema=public`, with no pool/connection limit, pool timeout or PgBouncer service. It would be incorrect to infer an exact connection count from concurrency 14. Actual capacity depends on the installed Prisma engine, effective URL, hardware, PostgreSQL settings and number of processes (`src/infrastructure/db/prisma.ts:1-2`; `src/main.ts:20-26`; `docker-compose.yml:2-51`).

History has an `(expedienteId, createdAt)` index. Hot case-specific inbox/action queries lack equivalent compound indexes: inbox declares only `(status, notBefore)`, actions only `(status, createdAt)` plus unique keys. Delivery lookup searches a JSON receipt `messageId`; opening detection searches JSON receipt template and message substrings. No corresponding JSON/search indexes are declared. Due-reminder selection also lacks a dedicated index on its pause/opt-out/due-time predicate. These are likely growing costs, not measured sequential scans (`prisma/schema.prisma:98-100`, `prisma/schema.prisma:102-121`, `prisma/schema.prisma:157-185`; `src/queue/action-executor.ts:247`; `src/core/workflow-service.ts:185`, `src/core/workflow-service.ts:229-230`; `src/core/automation.ts:11`). Inbox, message, action, audit and human-task tables have no retention bound in the audited lifecycle; BullMQ's 1,000-job retention does not limit PostgreSQL growth.

**RAG memory/CPU:** each model instance owns one retriever, shared across that process's cases. It loads all vectors into a `Float32Array` and caches them; it does not allocate a full index per client (`src/api/server.ts:76-81`; `src/adapters/ai/openai-compatible-conversation.ts:134-142`; `src/core/package-agent/rag-index.ts:67-74`, `src/core/package-agent/rag-index.ts:104-136`).

- Default dimensions: **512**; index-build embedding batch: **256**. Runtime retrieval returns up to **5** distinct examples from the top **20** scores (`src/core/package-agent/rag-index.ts:5-9`, `src/core/package-agent/rag-index.ts:129-131`).
- Local metadata contains **30,680 × 512** vectors (`.runtime/rag/examples-text-embedding-3-small.json:5-7`). The vector file's size matches **62,832,640 bytes = 59.921875 MiB**. Loading copies the read buffer, so transient vector storage can be roughly twice that, before strings and scores. This confirms a local artifact, not that its hash matches the currently configured package or that a runtime has loaded it.
- Each retrieval performs **15,708,160 dimension iterations** at that artifact size, then sorts all 30,680 scores: O(N×D + N log N), synchronously on the Node event loop. Keyword fallback also scans/tokenizes/sorts examples. Training-package loading reads all seven allowlisted files and parses the training sets in memory, adding memory beyond the vector array (`src/core/package-agent/rag-index.ts:80-87`; `src/core/package-agent/package.ts:13-43`, `src/core/package-agent/package.ts:58-61`).
- More application processes duplicate package/index memory. A loaded index stays cached; only missing/stale loads are rechecked after **5 minutes**. A rebuilt artifact is not reloaded when the existing cached status is `LOADED` (`src/core/package-agent/rag-index.ts:108-121`). There is no runtime query-embedding cache. Increasing inbound concurrency alone does not parallelize this synchronous CPU work.

**Outbox liveness:** a `RUNNING` action older than **10 minutes** is changed to `UNCERTAIN`, but normal dispatch queues only `PENDING`. An uncertain WhatsApp action then blocks inbox consumption until reconciled; this is a safe anti-duplicate boundary without an automatic liveness resolution. `AWAITING_DELIVERY` does not block the inbox, yet there is no action-age watchdog for a callback that never arrives. The **24-hour** callback rule applies to received but unmatched callback rows, not missing callbacks (`src/queue/workers.ts:38-46`; `src/core/workflow-service.ts:185`; `src/api/server.ts:167-174`).

The current failure-notice code prevents recursive notices: an action whose idempotency key begins `blocked-notice-` cannot create another fallback notice. This is a useful bound. A blocked primary action still creates a human task and a fallback that may itself be unsendable during the same outage; distinct primary actions can each create one such pair. Operational recovery remains necessary (`src/queue/action-executor.ts:98`, `src/queue/action-executor.ts:129-143`).

**4. Model freedom, deterministic control and off-topic derailment**

The model cannot directly write a state, invoke tools, validate a PDF, confirm a payment or complete a filing. It may propose one allowlisted option/event pair when local classification is unsupported, or generate reply text and a human-review flag. Option schema, state allowlist, exact event mapping and secure-button exclusions are validated in code; reply validation is schema/regex/URL validation, **not human review or semantic proof** (`src/core/conversation-agent.ts:79-123`, `src/core/conversation-agent.ts:157-188`; `src/core/conversation-policy.ts:262-306`). The provider is opt-in (`CONVERSATION_AI_PROVIDER` defaults to `none`); a disabled/unconfigured model leaves the local policy active (`src/config/env.ts:21`; `src/api/server.ts:72-81`).

Deterministic logic runs before and after the model: greetings, privacy/opt-out/human/payment rules, guidance progression, route-choice evidence checks and reviewed answers. Local definite options avoid a provider call. The FSM is a pure state/event function and the service only persists approved patch keys. Guided difficulty increments stored counters: with no certificate, the third failed attempt can offer alternatives; with a certificate, copy assistance begins after sufficient digital attempts/no-PC, and fallback follows a failed attempt when at least three copy-help attempts already exist (`src/core/conversation-agent.ts:84-108`, `src/core/conversation-agent.ts:198-281`; `src/domain/fsm/state-machine.ts:345-367`, `src/domain/fsm/state-machine.ts:1328-1332`; `src/core/workflow-service.ts:61-62`).

Legal/effect gates are separate: operator and client document review precede upload; payment requires an operator event plus current partner preapproval; final completion requires the verified filing/Dayana/delivery chain. Unsupported client events usually hold; completed/escalated states have their own handlers before the global conversational handler (`src/core/workflow-service.ts:49-55`, `src/core/workflow-service.ts:136-150`; `src/domain/fsm/state-machine.ts:1017-1036`, `src/domain/fsm/state-machine.ts:1118-1139`, `src/domain/fsm/state-machine.ts:1157-1193`, `src/domain/fsm/state-machine.ts:1270-1279`).

| Client input | Decision boundary and practical consequence |
|---|---|
| Claim status / when money arrives | Recognized phrases receive the office contact and no invented date, with `requiresHumanReview=false`; normally `CLIENT_SMALL_TALK` preserves the state. It still creates an action and increments version (`src/core/conversation-agent.ts:230-233`, `src/core/conversation-agent.ts:291`; `src/domain/fsm/state-machine.ts:1254-1262`; `src/core/workflow-service.ts:74-79`). |
| Ordinary price question | Reviewed cost explanation; questions are generally barred from selecting a route. However, the non-court reply asks again whether the client has a certificate even when that fact is already stored. In `MOBILE_TRIAGE_PC_CHECK`, a “yes” to this support question is subsequently interpreted as PC availability. The reply's question and deterministic pending answer can diverge (`src/core/conversation-guidance.ts:57-81`; `src/core/conversation-policy.ts:203-209`). |
| Bank account / transfer / invoice | Hardcoded `a que cuenta`, `iban`, `transferencia`, `factura` reply requires human review. In an ordinary active state this moves the entire case to `ESCALATED_HUMAN`, saves its prior state and pauses automation. That is an intentional whole-workflow hold, not a state-neutral side question (`src/core/conversation-agent.ts:226`; `src/domain/fsm/state-machine.ts:1261`; `src/core/workflow-service.ts:66`). |
| Novel out-of-scope question | Model may set `requiresHumanReview=true`, which can escalate through the same mechanism. In digital-guidance states a later heuristic suppresses some model handoffs and substitutes the pending question. Therefore model discretion is bounded but still affects whether work pauses; it is not merely wording freedom (`src/core/conversation-agent.ts:169-178`). |
| Repeated support answer | A final substring/equality check replaces **any** repeated reply with court/paid-company alternatives and `requiresHumanReview=false`, with no state or handoff exemption. It can undo a reviewed refusal/handoff candidate, suggest alternatives prematurely, or repeat an unrelated route offer after a second status question. It normally leaves the FSM state unchanged, creating a misleading conversational route (`src/core/conversation-agent.ts:283-291`). |
| “I sent it” / payment assertion | Text alone does not supply document/payment evidence; reviewed replies request the PDF, model replies are checked for completion claims, and the FSM still requires real document/operator evidence (`src/core/conversation-guidance.ts:87-96`; `src/core/conversation-policy.ts:299-305`; `src/domain/fsm/state-machine.ts:1017-1036`). |

Thus, **yes, an off-topic exchange can derail progress**, even without an unauthorized terminal state transition. There are three distinct mechanisms: an intentional global human hold; an answer that asks a question inconsistent with the saved step; and a same-state reply changing the version that external work depends on.

The last mechanism has a particularly concrete trace. A completion notice for version V is accepted and awaits delivery. A status question is processed because `AWAITING_DELIVERY` is not an inbox blocker; its support response increments the case to V+1. When the completion callback arrives, the action becomes `EXECUTED`, but `CLIENT_NOTIFICATION_DELIVERED` is not applied because versions differ. Only `DELIVERY_CONFIRMED_AFTER_STATE_CHANGE` is logged; the case remains in `HANDOFF_DAYANA`, and a repeat callback returns early because the action is already executed. Similarly, a pending non-WhatsApp filing/notice action can become `STALE` following an otherwise harmless support turn (`src/core/workflow-service.ts:74-79`, `src/core/workflow-service.ts:185`; `src/queue/action-executor.ts:69-72`, `src/queue/action-executor.ts:253-261`). These are static reachable traces, not claimed live reproductions.

**5. Top five risks at volume, ranked, with the smallest fixes**

| Rank | Risk and impact | Smallest corrective change to review |
|---|---|---|
| **1 — Critical** | **Cross-client memory contamination.** A shared agent’s mutable `memory` is overwritten per case; a turn awaiting classification can later read another case’s memory for its reply. Evidence: `src/api/server.ts:79-81`; `src/core/workflow-service.ts:233-234`; `src/core/conversation-agent.ts:58-60`, `src/core/conversation-agent.ts:118`, `src/core/conversation-agent.ts:167`. | Pass an immutable per-turn memory value explicitly through `turn`, `classify` and `respond`; remove the shared mutable field. Keep each model request’s memory bound to its case snapshot. Per-case locking cannot protect a process-wide field shared across different cases. |
| **2 — High** | **Conversation activity invalidates business progress.** Same-state replies advance the shared version, invalidating consent, staling pending CRM actions and potentially stranding a delivered completion notice. Evidence: `src/core/workflow-service.ts:74-79`; `src/api/server.ts:242`; `src/queue/action-executor.ts:72`, `src/queue/action-executor.ts:259-261`. | Make state-neutral, fact-neutral support replies independent of the business version: retain per-message action idempotency/audit but do not advance the version fencing consent/documents/effects. Keep checks for actual fact/state changes. For expired consent, issue a fresh bound request rather than accepting the stale one. |
| **3 — High** | **A slow case blocks limited workers and interrupts global dispatch.** Four inbound slots can be occupied for roughly 256 seconds each; reminder/callback lock failure aborts unrelated scheduling. Evidence: `src/queue/workers.ts:11-24`, `src/queue/workers.ts:35-48`; `src/adapters/ai/openai-compatible-conversation.ts:242-256`; `src/core/automation.ts:14`. | First isolate errors per case/callback and separate follow-up scheduling from outbox dispatch so one lock failure cannot skip unrelated work. Add one aggregate turn deadline/cancellation signal and coalesce inbound jobs per case. A subsequent larger improvement is generation outside the case lock, followed by generation/version revalidation before commit. |
| **4 — High** | **Failure recovery can freeze a conversation indefinitely.** An uncertain send blocks all further turns but is not dispatched automatically; missing delivery callbacks have no action-age deadline. The fallback recursion guard now exists, but does not resolve these holds. Evidence: `src/core/workflow-service.ts:185`; `src/queue/workers.ts:38-46`; `src/queue/action-executor.ts:129-143`; `src/api/server.ts:167-174`. | Add age alerts and an explicit operator reconciliation outcome for uncertain/undelivered effects; expose the blocking action and next required evidence. Deduplicate outage tasks per case/cause while retaining the existing fallback guard. Preserve the ban on blind resends and do not declare delivery without evidence. |
| **5 — Medium/High** | **Memory fields do not yet preserve dialogue meaning.** Summary columns have no runtime summarizer/reader; pending-question capture is unbound/stale-prone; deterministic answers ignore it; repeated-support logic can ask the wrong question or offer an unavailable route. Evidence: `prisma/schema.prisma:76-82`; `src/core/case-memory.ts:11-36`; `src/queue/action-executor.ts:113-118`; `src/core/conversation-agent.ts:283-291`; `src/core/conversation-guidance.ts:79-81`. | Bind pending questions to action ID/step/expected answer and clear them on resolution; make local support/repetition rules respect that contract and retain handoff flags. Populate minimal, provenance-backed client constraints/subroute/defer-until memory and pass it per turn. Map device `NONE` correctly and derive elapsed silence from the preceding inbound, not the just-ingested message. A summary must never grant consent or assert verified completion. |

Pool sizing, compound indexes, retrieval CPU isolation and fair queue scheduling remain necessary capacity work even after these five fixes. A defensible volume target requires real-system measurements of queue age, turn latency, lock failures, model timeout/fallback rates, DB pool wait, RAG CPU/RSS and unresolved outbox/human-task age. None of those throughput or operational outcomes is established by this source-only audit.
