# Setup test with mock data

The user explicitly authorized this setup test with mock business data. This is a scoped exception to older no-mock project guidance. It does not validate production or establish a real legal filing.

Run `npm run test:setup` after local PostgreSQL and Redis are available. The runner uses Node.js/TypeScript exclusively. It uses local `DATABASE_URL` and `REDIS_URL` from `ENV_FILE`, or this project's `.env` when `ENV_FILE` is unset. For example: `ENV_FILE=/absolute/path/apod-setup.env npm run test:setup`. Optional `SETUP_DATABASE_URL` and `SETUP_REDIS_URL` override those infrastructure connections for this test. No provider credentials or accounts are required.

The selected dotenv file is read and parsed in full. Only the two infrastructure URLs are retained from that parsed file; the input buffer is then cleared. The test constructs its mock configuration from those allowed URLs and generated test settings, never by copying `process.env` or the whole parsed file. Application configuration validation is pure, so importing the test's modules does not load provider credentials into the process environment. Provider keys, accounts, mappings, callback secrets and connector enablement are excluded, with an assertion that verifies this. No provider adapter is constructed from the process environment.

The real components exercised are Fastify HTTP, operator authentication, signed webhook validation, durable inbox and debounce, BullMQ workers, Redis locks, Prisma/PostgreSQL persistence, generated PDF parsing, content-addressed private storage, the state machine, and the action executor. WhatsApp, Kmaleon and Apudata are explicit offline port implementations. The first case is found by DNI through the same search-and-add API used by the panel; the selected project is read again before linking. A mock receipt means only that the in-memory simulated provider accepted an operation; it never means that Meta, Kmaleon or Apudata performed one. No email access, SMTP send, court session, account login or payment occurs.

Each run creates a random `apod_setup_<uuid>` PostgreSQL schema and `apod-setup-<uuid>` Redis queue prefix. Connections are rejected unless both database and Redis use a literal loopback host; the database must be `apoderamientos` or `apoderamientos_setup`. Prisma applies the repository's actual migrations to that isolated schema. The test never resets the normal schema, flushes Redis, or imports real clients, documents or certificates. Internal operator/webhook test keys are generated in RAM, are not printed, and are not written into `.env`.

Synthetic client names and every PDF page are labeled MOCK. The test verifies the five-page final route, missing human/client approval, duplicate inbound events, duplicate queue execution, signed delivery before completion, a provisional document that remains pending, revocation/reissue to a final document, and missing Airam/wrong-identity/negated-power rejection. A second actual HTTP server confirms that normal setup mode rejects WhatsApp verification, WhatsApp ingestion and Apudata callbacks with HTTP 503 even when artificial secrets are populated, with no inbox mutation. The paid route checks preapproval, approval identity, the EUR 35 amount, creation only after an operator's simulated payment evidence, and prevention of a duplicate order.

The latest report is `evidence/setup-test.json`; a permanent per-run copy and generated PDFs are in `.runtime/setup-tests/<runId>/`. Reports say `SETUP_WITH_MOCK_DATA`, identify their schema, and keep `productionVerified: false`. Successful runs remove only their own Redis queues. Both successful and failed runs retain their isolated database schema and local artificial files for inspection. On failure the report includes the outstanding case/action states, while secrets and raw extracted document text are excluded. Re-run creates a different schema and cannot overwrite the previous run.

A passing test demonstrates the setup works with the simulated provider contracts. Real provider API mappings, identities, credentials, real signed documents, actual court behavior and delivery still require separate authorized production verification.
